## 1. 产品概述

### 1.1 产品背景

职场人面对拒绝加班、汇报错误、请假、提不同意见、争取资源或与客户协商时，常常不是“不会写句子”，而是害怕说出口后的后果：对方会不会生气、追问、拒绝，或影响后续关系。

通用AI通常从“生成一段话”开始，但用户未必知道应该提供哪些背景，也难以判断生成内容的策略适用性。

### 1.2 一句话定位

**说话有谱是一款面向职场高压沟通的AI对话预演工具：先诊断用户的顾虑和底线，再给出三种沟通策略，并预演对方可能的回应。**

### 1.3 产品承诺

在重要的职场对话发生前，让用户从“不敢说”变成“心里有谱”。

### 1.4 非产品承诺

- 不保证准确预测他人的真实反应。
- 不替用户做重大人事、法律、医疗或安全决策。
- 不将AI结果包装成唯一正确话术。
- 比赛版不追求覆盖所有职场关系和场景。

## 2. 目标用户与需求

### 2.1 首批用户

**工作0–5年、经常需要面对上级或客户，但缺乏高压沟通经验的年轻职场人。**

### 2.2 核心任务（JTBD）

> 当我面对一场可能影响关系或利益的职场对话时，我希望在开口前看到不同说法及其可能后果，以便选择最符合自己底线的方案。

### 2.3 核心痛点

1. 不知道该不该说，害怕说错话承担后果。
2. 知道想表达什么，但不知道哪种策略更适合当前关系。
3. 能得到一段AI话术，却仍担心对方追问或拒绝时不知怎么接。
4. 在沟通前反复纠结，导致拖延、错过时机或情绪消耗。

### 2.4 高频场景池

1. 拒绝额外加班或临时任务。
2. 对领导或同事的方案有不同意见。
3. 不知道如何回复敏感消息。
4. 临时或长期请假。
5. 被安排超出职责范围的工作。
6. 项目延期或出错后向上级汇报。
7. 拒绝同事占用私人时间的求助。
8. 争取加薪、人力或其他资源。

## 3. 差异化与商业论证

### 3.1 核心差异

| 通用AI | 说话有谱 |
|---|---|
| 依赖用户自己编写完整提示词 | 主动诊断用户的真实顾虑和底线 |
| 通常只给一段优化后的文字 | 给出三种有明显策略差异的说法 |
| 重点是“怎么写” | 重点是“怎么决策和应对” |
| 生成第一句后结束 | 继续预演对方可能的回应 |
| 每次重新介绍对方 | P2可形成长期沟通对象画像和反馈闭环 |

### 3.2 商业主线

- **比赛主线：**B2C个人产品。
- **可持续方式：**免费基础体验 + 个人付费。
- **个人付费价值（P2假设）：**更多预演次数、连续追问、沟通对象档案、历史剧本、专业场景包和个性化建议。
- **远期扩展：**B2B新人培训、管理者沟通训练和销售客户沟通演练；不进入比赛MVP。
- **定价状态：**未经用户验证，比赛不宣称已验证的具体价格。

### 3.3 长期价值闭环（P2）

1. 用户建立“我的领导”“客户张总”等长期沟通对象。
2. 系统保留对方的性格、关注点与常见反应。
3. 沟通后由用户回填对方的实际回应。
4. 系统对比“预演”与“实际”，后续建议逐步贴近该具体对象。

### 3.4 信任边界

界面统一使用“可能反应”“对话预演”“一种应对预案”，不使用“对方一定会”“精准预测”等过度承诺。

## 4. 比赛版目标与范围

### 4.1 比赛成功标准

1. 主持人能在2–3分钟内完成一次核心流程演示。
2. 观众看完后能复述：“它不只帮你写，还会预演对方的反应。”
3. 翻开话术卡看到对方反应和表情，成为全流程的Aha时刻。
4. 两个主演示场景可重复、稳定跑通。
5. 真实AI失败时，能切换预设结果完成演示。

### 4.2 P0—比赛MVP必做

- 领导、甲方/客户两种关系类型。
- 男/女形象切换。
- 强势、严谨、随性、佛系、多疑五种性格标签。
- 自定义性格文字输入。
- 用户描述职场沟通困境。
- AI自主判断信息是否足够，最多追问2轮。
- 委婉、直接、迂回三种策略话术。
- 每版话术对应的“对方可能回应”和应对提示。
- 话术卡翻面交互。
- 预演反应与4类表情的映射。
- 复古羊皮纸剧本剧场的完整页面。
- 结构化AI输出、格式校验和失败兜底。
- 两个主演示场景的预设数据。

### 4.3 P1—有余力再做

- 一键复制某版话术。
- 用户针对某一版要求“再软一点”等语气微调。
- 返回上一幕修改人物设定或场景。
- 话术卡翻面音效或轻量动效。

### 4.4 P2—赛后产品化

- 平级同事、下属、跨部门协作方。
- 更多场景与性格标签。
- 用户登录、历史记录与多设备同步。
- 长期沟通对象档案。
- 对方实际反应回填和个性化学习。
- 完整连续角色扮演。
- 专业场景包和付费系统。
- B2B沟通培训、管理端和效果评估。
- 精细角色动画、声音或语音对话。

### 4.5 明确不做

- 比赛版不做登录、付费、管理后台、数据报表。
- 不为所有“关系×性格×性别×表情”组合单独绘制完整立绘。
- 不在比赛前建立复杂的个人记忆系统。
- 不追求手机端与桌面端同时精修；比赛优先桌面端。

## 5. 信息架构与核心流程

### 5.1 三幕结构

```text
第一幕·定角
选择对方的关系类型、性别形象和性格
        ↓
第二幕·起因
用户描述困境 → AI按需追问（最多2轮）
        ↓
第三幕·排演
生成三版话术 → 翻卡查看对方可能反应和表情
```

### 5.2 顶部幕次导航

- 显示“第一幕·定角 / 第二幕·起因 / 第三幕·排演”。
- 当前幕高亮，已完成幕显示完成状态，未解锁幕不可跳转。
- P0不必支持直接点击幕次跳转；P1可允许回到已完成的上一幕。

### 5.3 状态机

| 状态 | 触发条件 | 用户可见结果 |
|---|---|---|
| `setup` | 首次进入 | 人物和性格选择 |
| `describe` | 人物设定完成 | 场景输入框 |
| `clarifying` | AI判断缺少关键信息且追问次数<2 | 一句自然追问 |
| `generating` | 信息足够或已达2轮追问 | 排演加载态 |
| `results` | 三组话术校验通过 | 三张可翻面话术卡 |
| `fallback` | 超时、请求失败或格式连续校验失败 | 重试或载入当前主演示场景的预设结果 |

## 6. 详细功能需求

### 6.1 第一幕：对话对象设定（P0）

#### 6.1.1 关系类型

- 比赛版只显示两个选项：
  - 领导：直属上级。
  - 甲方/客户：外部合作方。
- 每个选项包含头像、关系名和简短说明。
- 单选；默认可选中“领导”，但必须有明确选中态。
- 关系类型决定AI中的身份上下文与人物资产键值。

#### 6.1.2 性别形象

- 提供“男 / 女”两个选项，单选。
- 性别只用于界面形象，默认不作为AI推断对方性格或反应的根据。
- 切换性别时，当前关系和性格选择不丢失。

#### 6.1.3 性格

- 预设标签：强势、严谨、随性、佛系、多疑。
- 预设标签单选。
- 提供自定义文本输入，示例：“急性子、嘴硬心软”。
- 当自定义输入非空时，自定义文本覆盖预设标签；清空后恢复最后一次预设选择。
- 自定义输入建议限制20个汉字或等价长度，去除纯空格内容。
- 性格仅是AI参考变量，不直接绑定固定表情。

#### 6.1.4 继续条件

- 关系、性别形象和性格均有有效值时，“进入下一幕”按钮可用。
- 进入第二幕后，页面保留一行对象摘要，例如：“当前对象：强势的男领导”。

### 6.2 第二幕：场景描述与挖掘（P0）

#### 6.2.1 场景输入

- 用剧本台词格式引导：“最近有什么话不知道怎么说？说给我听听。”
- 使用多行文本框，允许用户用自然语言描述。
- 空输入不可提交；去除首尾空格后再判断。
- 输入上限建议500个汉字或等价长度。

#### 6.2.2 AI需要掌握的信息

| 信息 | 来源 | 判断要点 |
|---|---|---|
| 关系/身份 | 第一幕 | 已知，无需再问 |
| 对方性格 | 第一幕 | 已知，作为语气与反应参考 |
| 用户真实顾虑 | 用户描述或AI追问 | 例如担心绩效、关系、客户信任或暴露错误 |
| 底线/弹性空间 | 用户描述或AI追问 | 例如完全不能接受，或可接受部分妥协 |

#### 6.2.3 追问规则

1. 如果已能合理推断真实顾虑和底线，直接生成话术。
2. 如果缺少会明显改变策略的关键信息，每轮只问一个最重要的问题。
3. 追问必须自然、短且易于回答，不使用问卷口吻。
4. 最多追问2轮；达到上限后必须生成结果。
5. 信息仍不完整时，结果顶部显示：“基于目前了解到的情况”。
6. 不重复询问第一幕已经选择的关系、性别形象或性格。

#### 6.2.4 对话展示

- 将每轮内容显示为剧本台词：“教练：……”“你：……”。
- 用户与教练使用不同颜色、缩进或角色标记，但正文必须保持高可读性。
- 进入生成状态后，禁止重复提交。

### 6.3 生成与加载（P0）

- 生成时显示与剧场主题一致的加载文案，例如：“正在为这场对话排戏……”。
- 加载期间保留已有台词，不展示空白页。
- 超时阈值由开发根据模型响应时间设置；超时后显示可理解的错误状态，不无限加载。
- 返回数据必须先通过字段、枚举和数量校验，再进入结果页。

### 6.4 第三幕：三版话术（P0）

#### 6.4.1 结果结构

结果页固定显示三张策略卡，顺序为：

1. **委婉版**：重视关系与情绪缓冲，但不能模糊用户底线。
2. **直接版**：明确表达结论、边界或请求，减少暧昧空间。
3. **迂回版**：将冲突从“我拒绝你”转向“我们如何解决问题”，例如提供替代方案、分步交付或资源调整。

三版必须在策略、句式和承担的关系风险上有明显区别，不允许只做同义词替换。

#### 6.4.2 卡片正面

- 策略名称。
- 可直接使用的口语化话术。
- 一句策略说明，告诉用户这版的取舍。
- “点击翻面，看对方可能怎么接”提示。
- P1可增加复制按钮；复制不得触发卡片翻面。

#### 6.4.3 卡片背面（核心Aha时刻）

- 当前沟通对象头像。
- 与反应分类对应的表情。
- 对方可能说出的具体回应，而不只是情绪形容。
- 一句“你可以如何接住”的应对提示。
- 明确标注“可能反应”，避免确定性表述。
- 点击同一卡片可翻回正面。
- 三张卡可独立翻转；不要求其他卡自动复位。

#### 6.4.4 重新开始

- 提供“排演另一场对话”操作。
- 触发后清空本次场景、追问和结果。
- P0可保留人物设定，以降低重复操作；用户可显式回到第一幕更换对象。

## 7. AI行为规范

### 7.1 系统角色

AI扮演“说话有谱”的职场沟通教练，不端着、不训话、不滥用职场术语。AI的任务是帮用户理清选择和预案，不是代替用户做价值判断。

### 7.2 生成原则

- 语言口语化，可直接用于微信、飞书、钉钉或面谈。
- 根据关系类型调整礼貌程度、权力距离与对风险的表达。
- 根据性格调整对方的可能反应，但不把性格标签当成确定事实。
- 不生成辱骂、威胁、歧视、恶意操控或明显欺骗性话术。
- 对敏感或高风险情况，提醒用户保留证据或寻求正式支持，但不做长篇说教。
- 预判反应必须是一句或数句具体可能回答，不得只输出“对方可能不悦”。

### 7.3 微调规则（P1）

- 用户只针对选中版本发出微调要求。
- AI必须在原策略和用户底线上微调，不重新生成全部三版。
- 微调后同步更新该版的可能反应、反应分类和应对提示。

## 8. AI结构化输出协议

### 8.1 追问响应

```json
{
  "status": "clarify",
  "clarification_question": "这次是完全不能接受，还是缩短时间后可以商量？",
  "context": {
    "real_concern": "担心影响年底评价",
    "flexibility": null
  }
}
```

### 8.2 生成响应

```json
{
  "status": "complete",
  "assumptions_notice": null,
  "context_summary": "你需要拒绝强势领导的周末加班安排，底线是周末无法到场，同时担心影响评价。",
  "options": [
    {
      "style": "soft",
      "label": "委婉版",
      "strategy": "先认可任务的重要性，再明确说明边界。",
      "script": "话术正文",
      "predicted_reaction": "对方可能说出的具体回应",
      "reaction_category": "angry",
      "follow_up_tip": "用户如何接住对方的一句应对提示"
    },
    {
      "style": "direct",
      "label": "直接版",
      "strategy": "策略说明",
      "script": "话术正文",
      "predicted_reaction": "具体回应",
      "reaction_category": "doubt",
      "follow_up_tip": "应对提示"
    },
    {
      "style": "indirect",
      "label": "迂回版",
      "strategy": "策略说明",
      "script": "话术正文",
      "predicted_reaction": "具体回应",
      "reaction_category": "smile",
      "follow_up_tip": "应对提示"
    }
  ]
}
```

### 8.3 枚举和校验

- `status`：只允许 `clarify | complete`。
- `style`：只允许 `soft | direct | indirect`，且每种恰好1条。
- `reaction_category`：只允许 `angry | awkward | smile | doubt`。
- `clarification_question`：在 `clarify` 时必填，且只能包含一个核心问题。
- `options`：在 `complete` 时必填且长度必须为3。
- 任一必填文本不得为空字符串。
- 追问轮数由应用状态机计数，不仅依赖模型自觉。
- 达到2轮后，应用必须要求 `complete`，并不再接受 `clarify`。

## 9. 表情映射与角色资产

### 9.1 表情枚举

| 类别 | 语义 | 视觉表现 |
|---|---|---|
| `angry` | 强硬拒绝、不悦、生气 | 皱眉、绷脸 |
| `awkward` | 勉强同意、为难、纠结 | 苦笑、纠结脸 |
| `smile` | 爽快答应、满意、认可 | 微笑、点头感 |
| `doubt` | 怀疑、追问、意外 | 挑眉、狐疑脸 |

### 9.2 解耦规则

- 性格影响AI生成的反应内容，不直接决定表情。
- 表情只由 `reaction_category` 决定。
- 关系类型和性别形象决定角色底图。
- 前端通过统一的资产解析函数选择底图与表情层，不将具体像素位置写入业务逻辑。

### 9.3 比赛版资产范围

- 2种关系×2种性别 = 4张角色底图。
- 每个底图支持4种表情层；如果五官坐标可复用，允许共用表情资产。
- 建议统一画布200×200 px，透明背景，由界面提供圆形色块底。
- 建议目录与命名：

```text
avatars/{role}/{gender}/base.png
avatars/{role}/{gender}/expressions/{reaction_category}.png
```

- 关系键：`leader | client`。
- 性别形象键：`male | female`。
- 表情键：`angry | awkward | smile | doubt`。
- 正式资产尚未交付时，允许沿用原型中的16×16像素网格作为占位，但不将占位细节变成正式资产约束。

## 10. 视觉与交互规范

### 10.1 核心方向

**复古羊皮纸剧本剧场风格。**

这不是一层可以随意删除的装饰，而是产品识别度和“对话排练”心智的一部分。

### 10.2 设计语言

- 背景：深酒红/暗幕布色，少量舞台聚光渐变。
- 主内容：暖米色羊皮纸或剧本纸，可以有纹理，但不影响汉字对比度。
- 点缀：聚光金、火漆红、古蓝等少量辅助色。
- 标题：可使用有印刷感的宋体/衬线中文字体。
- 正文：优先使用清晰、屏幕可读的中文字体，不为了复古牺牲阅读。
- 辅助元素：幕次、台词标记、节目单、印章或卡片编号。
- 避免：五线谱、声波、过量羽毛笔或复杂的欧式繁花。

### 10.3 交互原则

- 页面可有戏剧感，操作必须直觉。
- 主操作按钮在每一幕保持一致位置和样式。
- 所有可点击元素必须有悬停、选中或按下反馈。
- 翻卡动画建议0.4–0.6秒，不得阻塞快速阅读。
- 应支持用键盘聚焦和Enter/Space触发主要操作。
- 翻卡应提供减少动效的兼容方案。

### 10.4 桌面端优先

- 比赛主要适配桌面浏览器，目标视口宽度不低于1024 px。
- 主内容宽度保持在易阅读范围；三张卡可根据实际屏幕选择单列或三列，但不能因布局造成正文过窄。
- 小屏下不得内容溢出或无法翻卡；精细手机布局属于P2。

### 10.5 视觉验收标准

1. 无需讲解，首屏就能让人联想到剧本或舞台。
2. 汉字正文在比赛投影或笔记本上清晰可读。
3. 三种策略的颜色和标记一眼可分，但不破坏整体复古色系。
4. 卡片翻面后，头像表情、具体回应和应对提示构成全页最强层级。
5. 纸张纹理、阴影和装饰不影响按钮识别和文本对比度。

## 11. 异常、兜底与演示安全

### 11.1 普通异常

| 异常 | 用户反馈 | 系统处理 |
|---|---|---|
| 网络不可用 | “剧场暂时断线了” | 保留已输入内容，提供重试 |
| AI请求超时 | “这场排练比预想中久” | 取消无限加载，提供重试或兜底 |
| 返回不是有效JSON | 不向用户暴露技术错误 | 先内部重试1次，仍失败则进入兜底 |
| 字段缺失/枚举非法 | 不展示残缺卡片 | 校验失败，重试或兜底 |
| 用户空输入 | 就地提示“先说说发生了什么” | 不发起AI请求 |

### 11.2 比赛演示兜底

- 内置场景A、B的完整预设追问和生成结果。
- 预设数据使用与真实AI完全一致的数据结构，前端不区分渲染逻辑。
- 开发/演示模式可显式切换“真实AI / 预设演示”，但切换入口不必暴露给普通用户。
- 最终彩排前若真实AI仍无法稳定通过测试，现场主Demo改为预设演示，真实AI放入补充说明。
- 演示电脑必须事先本地打开一次，确保静态资产、字体和预设数据不依赖现场网络。

## 12. 两个主演示测试用例

### 12.1 场景A：拒绝强势领导的周末加班

**初始设定**

- 关系：领导。
- 性别形象：男（演示可切换为女）。
- 性格：强势。
- 用户输入：“领导让我周末加班，我不想去，但怕拒绝了影响年底评价。”

**预期诊断**

- 关系已知。
- 真实顾虑已知：年底评价。
- 底线/弹性不明确。

**预期追问**

> 这次是周末完全无法安排，还是只处理一小段时间也能接受？

**用户补充**

> 家里已经有安排，这周末确实去不了，但我今晚可以先整理交接。

**验收要点**

- 不应再追问性格或关系。
- 三版都必须坚守“周末无法到场”，不得把用户底线改成勉强答应。
- 委婉版应先认可紧急性，再给出今晚交接方案。
- 直接版应明确拒绝周末到场，同时给出不模糊的后续安排。
- 迂回版应将重点转向任务拆分、交接或其他资源。
- 三个可能反应应存在区别，并映射到合法表情枚举。

### 12.2 场景B：向多疑客户争取延期

**初始设定**

- 关系：甲方/客户。
- 性别形象：女（演示可切换为男）。
- 性格：多疑。
- 用户输入：“项目最终交付想延后三天，但客户一直觉得我们在拖，我怕他不信任我们。”

**预期诊断**

- 关系已知。
- 真实顾虑已知：客户信任。
- 弹性空间不明确：是否可分步交付。

**预期追问**

> 完整版必须延后三天，还是可以按原时间先交一个可验收的部分版本？

**用户补充**

> 可以按原时间先交核心流程，三天后再补齐完整版。

**验收要点**

- 三版话术都不得隐瞒延期事实。
- 至少一版明确提出分步交付、可验收节点与新时间表。
- 对方可能反应应体现“多疑”，例如追问延期原因、要求书面计划或对新日期表示怀疑。
- 不得因“多疑”标签生成侮辱性或刻板化描写。

## 13. 非功能需求

### 13.1 性能与稳定性

- 静态页面首次加载不依赖AI接口。
- 点击主操作后立即提供视觉反馈，避免用户重复提交。
- 表情切换和卡片翻面不因网络状态卡顿。
- 预设演示模式可在断网情况下完成全流程。

### 13.2 安全与隐私

- AI服务密钥不得直接出现在前端代码或公开仓库。
- 使用服务端或安全代理转发AI请求。
- 比赛版默认不持久化保存用户输入；如实际保存，必须明确说明。
- 日志不记录密钥、完整私密对话或其他敏感字段。
- 前端渲染AI文本时进行安全处理，不直接执行模型返回的HTML或脚本。

### 13.3 可用性

- 表单控件具备明确标签、焦点态和错误提示。
- 不仅依赖颜色区分选中状态和三种策略。
- 表情图像附带可理解的文本含义。
- 错误文案告诉用户可以做什么，不只显示“失败”。

## 14. 原型继承与修正清单

### 14.1 `demo-juben.html`

**继承**

- 暗幕布 + 米色剧本纸的总体构图。
- 顶部品牌区、三幕导航和剧本台词呈现。
- 委婉/直接/迂回三张翻面卡。
- 翻面0.55秒左右的交互节奏。

**修正**

- 原型的幕次仅为静态标题；正式版必须跟随应用状态更新。
- 原型一轮同时询问“领导严不严”和“是否有弹性”；正式版每轮只问一个最关键问题，并不重复询问已选性格。
- 原型卡片背面只有文本；正式版增加角色头像和对应表情。
- 原型为硬编码案例；正式版由统一结构化数据驱动。
- 修正原型中个别繁体字或拼写不一致。

### 14.2 `demo-roles-pixel-v2.html`

**继承**

- 性别、关系、性格三类状态解耦。
- 自定义性格输入覆盖预设标签的交互。
- 4种反应分类驱动表情的技术思路。
- 圆形色块背景 + 像素角色的视觉语汇。

**修正**

- 原型显示5个关系角色；比赛正式版只显示领导和甲方/客户。
- “表情映射预览”是开发验证工具，不进入普通用户的第一幕。
- 表情在第三幕由AI结果自动决定，用户不手动选择。
- 16×16实时绘制是占位方案；正式版应允许无缝替换为Figma导出的正式资产。

## 15. 开发与交付顺序

### 阶段1：核心闭环

- 确定项目技术栈和本地/线上运行方式。
- 搭建三幕页面和应用状态机。
- 完成人物选择、场景输入和三张卡片渲染。
- 先用预设JSON跑通完整流程。

### 阶段2：AI联调

- 实现追问计数和结构化输出校验。
- 接入AI请求和安全的服务端代理。
- 用两个主演示场景反复测试输出稳定性。
- 完成超时、重试、校验失败和预设兜底。

### 阶段3：视觉与资产

- 完成复古羊皮纸剧场视觉。
- 替换正式角色和表情资产。
- 优化选中、加载、翻卡和错误状态。
- 在比赛电脑和常见桌面视口做可读性检查。

### 阶段4：演示冻结

- 锁定比赛演示版本，停止增加新功能。
- 运行完整验收清单。
- 真实AI和预设模式各彩排至少3次。
- 准备线上地址、本地版本和必要截图/录屏三层兜底。

## 16. 验收清单（Definition of Done）

### 16.1 功能

- [ ] 领导与甲方/客户均可选择。
- [ ] 男/女形象切换不丢失其他状态。
- [ ] 5个预设性格与自定义性格规则正确。
- [ ] 空场景不发送AI请求。
- [ ] AI能在信息足够时直接生成。
- [ ] AI每轮只问一个问题，且最多2轮。
- [ ] 达到2轮后不再追问。
- [ ] 每次生成恰好返回委婉/直接/迂回三版。
- [ ] 三版话术策略有明显差异，不是同义改写。
- [ ] 每版包含具体可能回应和应对提示。
- [ ] 三张卡可独立翻转和翻回。
- [ ] 卡片背面表情与 `reaction_category` 一致。
- [ ] 两个预设演示场景在断网下可完整跑通。

### 16.2 视觉与交互

- [ ] 首屏具有明确的羊皮纸剧本/舞台感。
- [ ] 三幕导航反映真实当前状态。
- [ ] 正文在桌面浏览器与投影上清晰可读。
- [ ] 所有选择项和按钮有明确的默认、悬停、选中和禁用状态。
- [ ] 翻卡不闪烁、不透字、不裁切长文本。
- [ ] 头像和表情在不同卡片背面正确显示。
- [ ] 纹理、装饰和动效不影响主要操作。

### 16.3 稳定性与安全

- [ ] AI密钥不存在于前端资源中。
- [ ] 重复点击不会创建多个并发请求。
- [ ] 超时、断网、无效JSON和字段缺失都有可见处理。
- [ ] AI返回文本不会作为HTML/脚本执行。
- [ ] 预设演示与真实AI共用同一渲染结构。

### 16.4 比赛彩排

- [ ] 场景A在2–3分钟内完成。
- [ ] 场景B可作为替代演示或追问补充。
- [ ] 真实AI模式连续3次完整跑通。
- [ ] 预设模式连续3次完整跑通。

## 18. 比赛表达建议

### 18.1 30秒开场

> 职场人真正害怕的，往往不是不知道一句话怎么写，而是不知道发出去以后会发生什么。通用AI帮你写第一句话，“说话有谱”则陪你把整场对话提前排练一遍。

### 18.2 Demo叙事重点

1. 先用“拒绝周末加班”让观众立即共情。
2. 突出AI不急着写话术，而是先问清用户底线。
3. 快速展示三种策略的差异，不逐字朗读。
4. 翻卡时停顿，让观众看到对方表情和可能追问。
5. 用一句话收束：“我们不是替用户选答案，而是让他在开口前看见选择的后果。”

### 18.3 商业收束

> 产品从个人职场沟通预演切入，用免费体验降低门槛，通过连续预演、人物档案和个性化建议形成个人付费；成熟后可扩展到企业沟通培训。
