# 《说话有谱》比赛答辩 Q&A

> 口径原则：回答强调“结构化决策辅助 + 对话预演”，不声称精准预测他人，也不暴露模型内部思维链。

## 一、产品与价值

### Q1：你们解决的核心问题是什么？

用户真正焦虑的不是一句话怎么写，而是说出口以后对方会怎么回应、自己还能不能接住。说话有谱把沟通拆成“明确关系和性格 → 描述困境 → 澄清顾虑与底线 → 生成三种策略 → 预演对方可能反应”，帮助用户在真实沟通前进行低风险排练。

### Q2：目标用户是谁？

首批用户是工作 0–5 年、经常面对领导或客户、但高压沟通经验不足的年轻职场人。典型场景包括拒绝加班、汇报错误、项目延期、请假、争取资源和客户协商。

### Q3：为什么不直接用 ChatGPT、豆包或其他通用 AI？

通用 AI 当然可以生成话术，但用户需要自己写完整提示词，还要自己判断关系风险，并猜测对方下一句。说话有谱把这些步骤产品化：主动收集角色上下文，必要时追问，固定输出三种有取舍的策略，并给出具体的可能回应和接话提示。

### Q4：你们和普通聊天 Bot 的区别是什么？

Bot 通常是“用户问一句，模型答一句”的开放式聊天；说话有谱是一个有明确目标和边界的工作流。它不是让模型自由闲聊，而是让模型在固定状态机和固定输出协议内完成诊断、策略生成与反应预演。用户最后得到的是可比较、可执行的一组排演方案，而不是一段散文式回答。

### Q5：三种策略有什么实际区别？

- 委婉版：先承接关系或对方需求，再表达边界，优先降低情绪冲突；
- 直接版：明确结论、边界或请求，减少暧昧空间；
- 迂回版：把正面冲突转成替代方案，例如拆分任务、分阶段交付或调整资源。

三种策略在关系风险和执行成本上有不同取舍，不是简单替换几个同义词。

## 二、核心技术

### Q6：项目使用了什么技术栈？

前端使用 Next.js 16、React 19 和 TypeScript；样式采用 CSS Modules 与全局 CSS，视觉资产使用 SVG 撕纸蒙版和纹理图片；服务端使用 Next.js Route Handler；AI 输出使用 Zod 做结构化校验；代码托管在 GitHub，部署在 Vercel。

### Q7：调用的是哪个 AI API？

项目实现的是 OpenAI 兼容的 Chat Completions 接口：服务端向 `AI_BASE_URL/chat/completions` 发起 POST 请求，携带 `model`、system prompt、用户上下文和 `response_format: { type: "json_object" }`。

本地真实 AI 模式使用的是 DeepSeek 兼容接口和环境变量配置的模型；API Key 只存在服务端环境变量中。比赛公网 Demo 使用离线预设模式，因此评委打开链接不需要 API Key，也不会暴露密钥。

### Q8：为什么不用把 API Key 放在前端？

前端代码和浏览器请求都是用户可见的，密钥放在前端会被窃取。项目由服务端 `/api/coach` 统一调用模型，密钥只读服务端环境变量，`.env.local` 也被 Git 忽略，仓库只保留 `.env.example`。

### Q9：系统是怎么进行“推理”的？

这里的“推理”不是暴露模型内部思维链，而是把沟通判断拆成可验证的步骤：

1. 读取关系、性格、场景和历史追问；
2. 判断是否缺少会明显改变策略的关键信息；
3. 若缺信息，只提出一个最关键问题，最多两轮；
4. 信息足够后，分别生成 soft、direct、indirect 三种策略；
5. 为每种策略生成具体的可能回应、反应类别和接话建议；
6. 用 schema 校验结果，合格后才交给前端展示。

模型的内部生成过程不直接展示给用户，产品展示的是经过协议约束和校验后的结果。

### Q10：AI 如何判断要不要追问？

Prompt 明确要求模型优先判断“真实顾虑”和“底线/可接受弹性”。如果缺少的信息会明显改变沟通策略，就返回 `clarify`，每轮只问一个自然、简短的问题；如果信息已经足够，直接返回 `complete`。达到两轮上限时，服务端会强制要求返回完整结果。

### Q11：AI 输出为什么稳定？

我们没有直接把一段自由文本渲染到页面，而是规定严格 JSON 协议。完整结果必须恰好包含 soft、direct、indirect 三种策略，每张卡必须有话术、策略说明、具体可能回应、四类反应之一和 follow-up tip。Zod 在服务端校验字段、枚举、数量和非空文本，失败会重试或进入兜底。

### Q12：如果模型返回格式错误怎么办？

服务端最多进行两次提供方尝试；对超时、HTTP 5xx、无效 JSON 或 schema 错误等可恢复问题进行重试。仍失败时返回可理解的错误状态，并允许使用当前主演示场景的离线预设结果，保证比赛流程不中断。

### Q13：项目有没有真正的后端？

有。Next.js 的 `/api/coach` 是 Node.js Runtime 的服务端 Route Handler，负责请求校验、AI 调用、超时控制、错误映射和结果校验。页面和 API 一起部署在 Vercel，不是只有静态页面。

### Q14：为什么比赛版采用预设模式？是不是没有 AI？

项目同时支持真实 AI 和 preset 两种模式。真实模式用于开发和能力验证；比赛公网 Demo 使用确定性预设，是为了避免网络、配额或模型波动影响现场体验。预设模式保留完全相同的三幕交互和结果结构，所以评委仍能完整体验产品价值。正式产品可切换真实 AI，并继续保留兜底机制。

## 三、工程与体验设计

### Q15：为什么要设计成三幕剧场，而不是普通表单？

三幕结构对应用户真实的心理过程：先明确“和谁说”，再理清“发生了什么”，最后练习“怎么说、对方怎么回”。羊皮纸、撕拉边缘和翻卡不是纯装饰，而是把抽象的沟通预演变成可理解、可记忆的舞台隐喻。

### Q16：一键载入主演示场景解决什么问题？

比赛演示不能依赖临场组织输入。一键载入“周末加班”“客户延期”等场景，可以快速进入完整闭环，也让测试结果可重复。真实用户仍然可以从空白场景开始输入自己的问题。

### Q17：为什么沟通困境必填，但追问可以跳过？

没有沟通困境就没有可生成的内容，因此场景是必要输入；追问只是帮助模型补充信息，不应该成为用户的阻碍。用户可以直接跳过追问，系统会基于当前信息生成结果，并在必要时标注假设。

### Q18：如何考虑可用性和移动端？

页面使用清晰的三幕进度、角色摘要、按钮禁用态和字数提示；第三幕底部操作区预留安全间距，避免撕纸边缘遮挡按钮。比赛优先保证桌面演示完整，移动端保持基本可用，后续再做专项精修。

## 四、可靠性、边界与伦理

### Q19：它能精准预测对方吗？

不能，也不应该这样承诺。系统提供的是基于当前关系、性格和场景的“可能反应”，帮助用户准备多个预案，而不是替用户断言对方一定会怎么做。界面和 Prompt 都避免使用“精准预测”“一定会”等确定性表达。

### Q20：会不会替用户做职场决策？

不会。AI 扮演的是沟通教练，帮助用户看清顾虑、底线和表达选择，不替用户决定是否辞职、是否承担法律责任或做其他重大人事、医疗、安全决策。

### Q21：用户隐私如何保护？

比赛版不要求登录，不建立长期个人档案；请求只携带完成当前排演所需的角色和场景信息。API Key 不发送到客户端，也不上传到 GitHub。产品化后若加入历史记录，需要增加明确的存储说明、删除能力和权限控制。

### Q22：模型出现偏见或不合适建议怎么办？

Prompt 明确禁止根据性别推断性格或反应，并要求使用可能性表达。输出经过字段和枚举校验，但语义安全仍需人工和用户测试持续评估。后续可增加敏感场景识别、风险提示和人工审核策略。

## 五、商业与未来规划

### Q23：商业模式是什么？

比赛阶段定位为 B2C 个人产品，基础体验免费；赛后可围绕更多预演次数、专业场景包、历史剧本、沟通对象档案和连续训练提供个人付费能力。B2B 新人培训、管理者训练和销售沟通演练是远期方向，不作为当前 MVP 的既成收入承诺。

### Q24：赛后最值得做的功能是什么？

优先做“长期沟通对象档案 + 实际回应回填”。用户可以保存“我的领导”“某客户”等对象，并在沟通后记录真实回应，系统比较预演与实际，逐步形成更贴合具体对象的建议。这是产品建立长期壁垒的方向。

### Q25：如何验证产品是否有价值？

先观察三个指标：用户能否在 2–3 分钟内完成一次排演、是否愿意在真实沟通前重复使用、以及翻卡后的预演内容是否比单纯话术更能降低焦虑。进一步通过用户访谈和 A/B 测试验证留存、场景复用率和付费意愿。

### Q26：如果评委只记住一句话，你希望是什么？

**通用 AI 帮你写出第一句话，说话有谱帮你预演说出口之后怎么办。**
